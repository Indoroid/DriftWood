# Qwen3.8 27B CPU dense streaming plan

## Observed boundary

The local Q4_0 GGUF reports `general.architecture=qwen35`, 64 trunk layers, 65 total layers, 866 tensors and a 15,049 MiB CPU mapped tensor buffer. It has no MoE experts; no multimodal projector file is available. The text model loads and builds CPU graphs, but a full forward pass was killed on this 14 GiB host. Treat that as a memory limit, not a validated 27B inference run.

The separate `bmoe/expert-ready-hook` llama.cpp fork now offers a CPU `MUL_MAT` readiness callback. It keeps the existing `MUL_MAT_ID` expert callback and native ggml kernels. The callback only waits for a complete `src0` matrix; it does not own storage, read files or stream rows. Keep `use_extra_bufts=false` and the model's native GGUF tensor layout. No cwen repack or custom numerical kernel is needed.

## Implement in the consuming runtime

1. Add a dense streaming mode alongside the existing MoE mode. Accept a model with zero experts instead of entering the `no MoE expert tensors captured` failure in `core/src/engine/session_open.cpp`. Leave the MoE path and its expert hook intact. The mode must also run serially with stock llama.cpp through the existing public eval callback; use the fork hook only for overlap.
2. Reuse `read_gguf_meta` and `GgufOffsets` to map each GGUF tensor to a shard, byte offset and size. Reuse the graph capture in `RouterHook` to identify weight leaves and their consumers. Make that capture usable without a MoE recipe. Its current full warm-up decode is unsuitable for this 27B file on a 14 GiB host: capture node sources during scheduler `ask` callbacks, then abort computation early, before a full model pass. Prove this capture pass stays within the memory budget on the actual GGUF. Group aliases of the same file range as `DenseTensorRef` already does. Validate every streamed matrix's GGUF size, ggml type, strides and backing pointer. Keep small norms and SSM control tensors resident; the existing row-gather policy may serve an embedding only if capture proves it is exclusively gathered.
3. Reuse `DenseWeights` ownership and `platform_io` reserve/commit/evict primitives to give every streamed matrix a stable virtual address before execution. Rebind tensor pointers once, before real inference, as the current anonymous policy does. Commit only the physical pages needed for an active window. Reclaim a matrix after its last graph consumer; never rebind pointers while compute is active. Keep shared output weights and tied aliases together.
4. Choose a fixed resident set from the measured RAM budget and tensor sizes. Reserve RAM for KV/recurrent state, compute buffers, the I/O window and the OS. Pin that set across tokens. Stream the remainder through a bounded window. A cyclic LRU over a greater-than-RAM dense pass can evict each matrix immediately before its next use, causing near-zero cache hits and repeated SSD faults; a fixed set avoids that pattern. Use `DenseWeights::sample_residency`, major faults and actual `FileReader::read_bytes` to check the budget.
5. Add a small dense scheduler around the existing `FileReader`, with one or two positioned I/O lanes and a strict byte/window cap. Read exact GGUF tensor ranges, ideally coalescing adjacent required ranges, into their canonical backing. Publish completion per matrix with release/acquire synchronization. The fork hook waits for `src0`; an I/O error or cancellation wakes it and returns false so the graph aborts. The mainline serial path fills the matrix before its eval callback permits the node. No page-cache sweep of the entire file during decode.
6. Prefetch the next known matrix or layer while the current matrix computes. The dense graph order is deterministic, so the MoE `predict-prefetch` router is unnecessary and would only add gate work. Adapt the `io-two-wave` scheduling idea: publish the first required projection of a layer immediately, then stage later projections while the I/O lanes work. This can reduce first-matrix wait and staging pressure. It cannot reduce the compulsory bytes read for a dense token. Start with one-layer lookahead; tune the window only from measured stall, read amplification and resident fraction.
7. Expose dense mode, resident budget, window size and lane count through `RunConfig` and the CLI. Reuse existing I/O and stall metrics; report physical read bytes, major faults, resident fraction, callback wait and peak RSS separately for prefill and decode. Do not reuse MoE cache-hit or prediction metrics for dense weights.

## Verification gates

- Unit-test GGUF offset/alias matching, stable backing, last-consumer eviction, cancellation and failed reads. Exercise Q4_0 and a second native type with one and multiple CPU workers.
- Compare streamed versus resident logits byte for byte for prefill and decode. Test serial mainline and fork overlap paths. Keep the existing MoE identity gates passing.
- On a host with enough memory, run the exact 27B GGUF and record peak RSS, swap activity, major faults, actual SSD bytes and tokens/s across mmap, fixed-resident serial, overlap and two-wave modes. A 14 GiB host cannot establish a successful full 27B decode from the current mmap baseline. Do not claim lower SSD traffic or negligible throughput cost until these measurements exist.
